03 // AI Security

AI systems introduce an attack surface traditional application testing doesn't cover.

A modern AI product is rarely just a model behind an API. A typical LLM application chains together user input, orchestration logic, retrieval systems, tool-calling, and increasingly autonomous agent loops. Every boundary between those pieces is a place where trust assumptions can break down.

Prompt injection, insecure output handling, excessive agency, and retrieval-time data poisoning rarely surface in a conventional web application review. Testing them means assessing the model, the application built around it, and the interaction between the two, together and by hand.

  • Direct & indirect prompt injection
  • Insecure output handling
  • Excessive agency & tool misuse
  • System prompt & guardrail bypass
  • Training / retrieval data exposure
  • Plugin & supply-chain risk

INPUT SURFACE

User & client application
  • Direct prompt injection
  • Jailbreak techniques

THE MODEL

LLM core

Tool use / function calling

Tool abuse, SSRF, unsafe actions

RAG / retrieval

Indirect injection, data poisoning

Agent loops

Goal hijacking, unbounded autonomy

OUTPUT SURFACE

Application & external systems
  • Insecure output handling
  • Excessive agency
  • Sensitive data exposure

04 // Methodology

An authorised, evidence-driven process, every time.

No engagement starts without clear scope and authorisation. No finding ships without manual validation. The process is consistent; the testing is tailored to what you’ve actually built.

  1. 01

    Scope

    Define target systems, threat model, rules of engagement, and success criteria before any testing begins.

  2. 02

    Discover

    Map the real attack surface: endpoints, data flows, trust boundaries, model and agent integrations, dependencies.

  3. 03

    Assess

    Apply manual, adversarial testing techniques informed by current attack patterns and the system’s actual architecture.

  4. 04

    Validate

    Every finding is manually re-verified and exploited where safe to confirm real-world impact. Not unverified scanner output.

  5. 05

    Report

    Evidence-backed reporting: clear reproduction steps, business impact, and severity grounded in actual risk.

  6. 06

    Remediate

    Practical, prioritized remediation guidance, with support through fix verification. Not just a list of problems.
